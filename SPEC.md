## 1. Видение

1C:EDT построена на Eclipse и использует EGit/JGit. Стандартные операции повседневной
работы с Git (подтянуть изменения, не тревожа локальные правки; быстро убрать всё в стеш;
закоммитить в другую ветку; отменить последний коммит) в EDT требуют ручной цепочки
действий. В VS Code эти же сценарии — одна команда. Этот плагин закрывает разрыв: набор
потоковых операций «одно действие вместо цепочки».

Целевой пользователь — 1С-разработчик, работающий в EDT с Git-репозиторием
(ветвление по задачам, групповая разработка, миграция с хранилища).

## 2. Цели и не-цели

### 2.1 Цели
- Каждая операция — одна команда с понятным результатом или понятной ошибкой.
- Ни одна операция не должна приводить к потере незакоммиченных изменений пользователя.
- Плагин не дублирует существующий функционал EGit (история, staging, diff), только
  закрывает отсутствующие потоковые сценарии.

### 2.2 Не-цели (явно исключено)
- Визуализация истории / commit graph / blame / рефлог-визуализации — не делаем.
- Интерактивный ребейз — **уже есть в EDT** (см. 3.3), не дублируем.
- Работа с хранилищем конфигураций (1С Storage) — только Git.
- Серверные интеграции (создание MR, code review, уведомления) — не делаем. Единственное
  исключение: генерация ссылок «открыть в браузере» (§5.12).
- Worktrees, partial staging, 1С-специфичный мерж модулей по методам — не делаем.

### 2.3 Целевая среда (уточнено 2026-09-30)
- **Прод (цель установки): Windows, EDT 2025.2.6** — версия, стоящая на продуктиве.
- **Разработка: macOS** (Apple Silicon, EDT x86_64 под Rosetta).
- Код плагина — только архитектурно-независимый (чистый Java/SWT, без нативных
  вызовов, без привязки к путям/кодировкам ОС). Проверка на Windows — перед
  каждым релизом (ручной чек-лист §6.7 на EDT 2025.2.6).
- Порядок реализации: от наиболее безопасных команд к рискованным (без сети и
  перемещений по веткам — первыми). Первая итерация: §5.2–5.3.

## 4. Архитектура

### 4.1 Идентификация
- Namespace плагинов: **`dev.edt.gitflow`** (сторонний, не пересекается с `com._1c.*`).
- Продуктовое имя: «Git Flow».

### 4.2 Состав
Два OSGi-бандла, Maven/Tycho-сборка:

| Бандл | Слой | Содержимое |
|---|---|---|
| `dev.edt.gitflow.core` | headless-логика | Операции над репозиторием (JGit), без SWT/UI. Зависимости: `org.eclipse.jgit`, `org.eclipse.core.resources`, `org.eclipse.core.runtime`, `org.eclipse.egit.core` (маппинг проект→репозиторий). |
| `dev.edt.gitflow.ui` | UI | Команды, handlers, меню, диалоги, key bindings. Зависимости: `dev.edt.gitflow.core`, `org.eclipse.ui`, `org.eclipse.egit.ui` (только публичное API), `org.eclipse.jface`. |

Правило: вся Git-логика — в core, UI-бандл не вызывает JGit напрямую (только через core).
Так логика тестируется headless-без UI.

### 4.3 Ключевые точки интеграции
- Проект → репозиторий: `org.eclipse.egit.core.project.RepositoryMapping.getMapping(IProject)`.
- Кеш репозиториев воркспейса: все маппинги через `RepositoryMapping.getProjectMappings()`.
- Выбор «текущего» репозитория: по выделению (project/file), активному редактору,
  либо единственному репозиторию воркспейса. Правила в 6.1.
- Refresh воркспейса после операций: операции идут в `Job` (`org.eclipse.core.runtime.jobs`),
  по завершении — обновление ресурсов (JGit меняет файлы на диске; EDT/Big Model должна
  переиндексировать). Ориентир на поведение EGit после checkout/pull.
- Команды: `org.eclipse.ui.commands` + `org.eclipse.ui.handlers` + `org.eclipse.ui.menus`
  (собственная группа меню; не встраиваться в `egit.menu.advanced` — точку может двигать 1С).

### 4.4 Совместимость
- **Цель: EDT 2025.2.6 на Windows (прод).** Верхние рейнджы версий не ограничивать
  жёстко: egit/jgit — `[6.0.0,8.0.0)` (в 2025.2 может быть EGit 7.x), чтобы один
  артефакт работал и на 2026.1, и на 2025.2.6.
- Использовать только стабильные API JGit (`org.eclipse.jgit.api.*`) и публичное API
  EGit (`org.eclipse.egit.core.project.RepositoryMapping`); не использовать
  internal-пакеты egit/jgit.
- Java 17 (BREE). Код без привязки к ОС.
- Пока на Mac не установлена EDT 2025.2.6, сборка ведётся против пула 2026.1
  (`releng/edt-2026-1.target`) — поставить 2025.2.6 через 1cedtstart и добавить
  второй .target-файл (открытый вопрос §9).

## 5. Команды (спецификации)

Каждая команда: сценарий, поведение, ошибки. Названия в UI задаются через
`plugin.properties`/`plugin_ru.properties`; привычные Git-команды Pull и Push
не переводятся.
Общие правила: §6.

### 5.1 Smart Pull — «Pull»

**Сценарий:** подтянуть изменения из upstream, не тревожа локальные незакоммиченные правки.

**Поведение:**
1. Определить репозиторий и текущую ветку (6.1).
2. `git fetch` для сконфигурированного upstream.
3. Если локальных незакоммиченных изменений нет — обычный pull.
4. Если есть — rebase с autostash: локальные изменения автоматически прячутся и
   возвращаются поверх подтянутых коммитов.
   Реализация на выбор (выбрать при имплементации, зафиксировать в коде):
   - нативная: `rebase.autostash=true` + `pull --rebase` через JGit (`PullCommand`);
   - явная: `StashCreateCommand` → pull → `StashApplyCommand`.
   Критерий выбора: надёжность на конфликтах; нативная предпочтительнее, если JGit
   корректно обрабатывает конфликт autostash (проверить на тестовом репозитории).
5. Результат — понятное сообщение: «подтянуто N коммитов, локальные изменения
   восстановлены» / «уже актуально» / «конфликт при rebase — разрешите вручную».

**Ошибки:** нет upstream — сообщить и предложить настроить; сетевая ошибка — откат
к исходному состоянию (stash не удалять до успешного apply); конфликт rebase —
остановиться, оставить состояние как git оставил, показать инструкцию.

Если upstream отсутствует, команда после подтверждения ищет одноимённую ветку в
`origin`, настраивает tracking и продолжает получение. Если ветки нет, предлагает
первую отправку через Smart Push; рабочие файлы не трогает.

### 5.2 Quick Stash — «Быстрый стеш»

**Сценарий:** одна команда — убрать все незакоммиченные изменения без диалога.

**Поведение:**
1. Проверить наличие изменений; если пусто — сообщить «изменений нет».
2. `StashCreateCommand` с автоименем: `WIP @ <ветка> <дата-время>`; untracked — по
   настройке (по умолчанию включены).
3. Сообщение: «Спрятано в стеш “<имя>”». Действие в сообщении (линк): «Отменить»
   (= немедленный apply этого стеша).

**Ошибки:** пустая рабочая область — не ошибка, а нотификация.

### 5.3 Quick Pop — «Вернуть последний стеш»

**Поведение:** `StashApplyCommand` последнего стеша + `StashDropCommand` после успешного
apply (pop). Если стешей нет — нотификация. При конфликте apply — стеш **не** удалять,
показать, что произошло, дать ссылку на штатное view «Git Stashes» (оно уже есть в EGit).

### 5.4 Commit to New Branch — «Коммит в новую ветку…»

**Сценарий:** закоммитить изменения в новую ветку, не оставаясь в ней.

**Поведение:**
1. Диалог: имя ветки (валидация: нет такой ветки), чекбокс «вернуться в исходную ветку
   после коммита» (по умолчанию — да), чекбокс «отправить новую ветку в origin» (нет).
2. Если staged пуст — предложить закоммитить все отслеживаемые изменения или отмену.
3. Создать ветку от HEAD (`CreateBranchCommand`), переключиться; если переключение
   блокируется грязным деревом — автоматический stash → checkout → apply
   (autostash-примитив, §6.3).
4. Коммит с сообщением из диалога (или сгенерированным, §5.11).
5. Если выбран возврат — checkout обратно (с autostash-примитивом при необходимости).

**Ошибки:** имя ветки занято — запрет; конфликт при возврате — оставить пользователя
в новой ветке с понятным сообщением, изменения не терять.

### 5.5 Move Last Commit to Branch — «Перенести последний коммит в ветку…»

**Сценарий:** HEAD-коммит оказался не в той ветке; перенести его в другую ветку.

**Поведение:**
1. Диалог: локальная целевая ветка (дерево по `/`, поиск, избранное) или новая,
   чекбокс «вернуться». Удалённые ветки не предлагаются для переноса коммита.
2. Запомнить `C = HEAD`, исходную ветку `B`.
3. Целевая ветка `T`: checkout (autostash-примитив при грязном дереве).
4. Cherry-pick `C` в `T` (`CherryPickCommand`; если cherry-pick пустой из-за идентичности
   содержимого — это успех, не ошибка).
5. В `B`: после успешного переноса и проверки чистого дерева `ResetCommand`
   (hard, HEAD~1). Пользовательские незакоммиченные изменения к этому моменту
   находятся в стеше; mixed оставил бы содержимое перенесённого коммита в рабочей
   области исходной ветки и фактически продублировал его.
6. Вернуться в `B` (если выбрано), autostash-примитив при необходимости.

**Ошибки:** cherry-pick конфликт — остановиться, показать состояние; reset в `B` не
выполнять (коммит остаётся в `B`, пользователь разрешает конфликт в `T`).

### 5.6 Undo Last Commit — «Отменить последний коммит»

**Сценарий:** последний коммит «не то/не туда» — вернуть его изменения, не теряя их.

Обоснование: 1С скрыла штатный Reset из UI EDT (activity в `com._1c.g5.v8.dt.egit.ui`),
пользователи лишены этой операции.

**Поведение:**
1. Проверка безопасности: если HEAD уже отправлен в origin (коммит входит в
   соответствующий remote-tracking ref) — модальное предупреждение «коммит уже на
   сервере; отмена потребует force push» с обязательным подтверждением.
2. Диалог: режим — «оставить изменения в индексе» (soft, по умолчанию) или
   «вернуть в рабочую область» (mixed).
3. `ResetCommand` (HEAD~1) выбранного режима.
4. Сообщение: «Коммит «<тема>» отменён, изменения <в индексе/в рабочей области>».

**Ошибки:** HEAD — merge-коммит или состояние не SAFE — отказ с объяснением;
отсутствие коммитов (пустая ветка) — отказ.

### 5.7 Smart Checkout — «Переключиться на ветку…» (умное)

**Сценарий:** переключение ветки, которое не падает на грязном дереве (аналог поведения
VS Code с autostash).

**Поведение:**
1. Диалог: дерево локальных и удалённых веток, сгруппированных по `/`, поиск,
   избранное для репозитория и поле создания новой ветки от HEAD. Выбор удалённой
   ветки создаёт локальную tracking-ветку, если её ещё нет.
2. Если цель == текущая ветка — отмена с нотификацией.
3. Если рабочее дерево чистое — обычный `CheckoutCommand`.
4. Если грязное — autostash-примитив (§6.3): stash → checkout → apply; при конфликте
   apply оставить стеш и сообщить (view «Git Stashes»).

**Ошибки:** checkout-конфликт (файлы пересекаются с изменениями и stash не спасает) —
остановиться до потери: состояние как у git, понятное сообщение.

### 5.8 Smart Push — «Push»

**Сценарий:** перед отправкой проверить удалённую ветку, при необходимости
подтянуть её изменения, затем выполнить push одной командой.

**Поведение:**
1. Smart Pull (§5.1) целиком, включая все его проверки и ошибки.
2. При успехе — `PushCommand` в upstream текущей ветки.
3. Если upstream не настроен — предложить «настроить upstream в origin/<ветка>»
   (записать `branch.<name>.remote/merge`).
4. Итоговое сообщение: «Подтянуто N, отправлено M» / «Уже синхронно».

**Ошибки:** push rejected (ветка на сервере ушла вперёд между pull и push) —
предложить повторить Smart Push; сетевая ошибка — показать, что pull прошёл, а push — нет.

Если upstream отсутствует, команда после подтверждения делает fetch `origin`:
существующую одноимённую ветку связывает и синхронизирует, новую публикует без
force и только после успешной отправки сохраняет tracking-настройку.

### 5.9 Multi-repo Smart Pull — «Подтянуть все проекты»

**Сценарий:** в воркспейсе EDT несколько проектов из разных репозиториев — подтянуть все.

**Поведение:**
1. Собрать все git-репозитории воркспейса через `RepositoryMapping` всех проектов.
2. Последовательно выполнить Smart Pull (§5.1) для каждого, с прогрессом
   «Репозиторий i из N».
3. Сводный отчёт (окно/нотификация): по каждому репозиторию — «подтянуто N» /
   «уже актуально» / «ошибка: <причина>». Ошибка одного не прерывает остальные.

**Ошибки:** репозиторий без upstream — в отчёт как ошибка настройки, продолжать.

### 5.10 Commit Guards — «Проверки перед коммитом»

**Сценарий:** дешёвые командные правила, предотвращающие типовые ошибки: коммит в
защищённую ветку, сообщение без номера задачи.

**Поведение:**
- Реализация — собственная команда «Безопасный коммит…» (свой мини-диалог: сообщение,
  правила), а не перехват штатного диалога EGit (встраивание в чужой диалог — хрупко).
- Правила (настраиваются, §6.8):
  - Защищённые ветки: список (по умолчанию `master`, `main`, `develop`). Коммит в них —
    модальное подтверждение с явным «я понимаю».
  - Шаблон сообщения: regex; несовпадение — блок с подсказкой формата.
- В диалоге показывается статус проверок; нарушение блокирующего правила отключает
  кнопку «Закоммитить» (или требует подтверждения для неблокирующих).

**Ошибки:** отсутствие изменений — стандартная нотификация.

### 5.11 Commit Message Generator — «Сгенерировать сообщение коммита»

**Сценарий:** сообщение из имени ветки по шаблону. Пример: ветка
`feature/JIRA-1234-dogovora` → «JIRA-1234: » в начале сообщения.

**Поведение:**
1. Взять текущее имя ветки; применить regex-настройку извлечения ключа задачи
   (по умолчанию `([A-Z]+-\d+)`).
2. Составить сообщение по шаблону настройки (по умолчанию `<ключ>: <тема вручную>`).
3. MVP: положить результат в буфер обмена и показать его; подстановка в диалог
   коммита — только через «Безопасный коммит» (§5.10).
4. Если ключ не найден — нотификация «шаблон не сопоставился, проверьте настройки».

### 5.12 Open in GitLab — «Открыть в GitLab»

**Сценарий:** одна команда — открыть в браузере текущий файл / ветку / коммит на GitLab.

**Поведение:**
1. Определить репозиторий (6.1); взять `remote.origin.url`; привести к base URL
   (убрать `.git`, привести `git@host:group/proj.git` → `https://host/group/proj`).
2. Команды меню:
   - «Открыть файл в GitLab» — URL `…/-/blob/<ref>/<путь>`; ref = хеш HEAD (постоянная
     ссылка), опция настройки — использовать имя ветки.
   - «Открыть ветку в GitLab» — `…/-/tree/<ветка>`.
   - «Открыть коммит в GitLab» — `…/-/commit/<хеш HEAD>`.
3. Открытие через `java.awt.Desktop` (fallback — копирование URL в буфер).
4. Хост определяется по URL: `gitlab` (включая self-hosted) — шаблоны выше; прочие
   (github/bitbucket) — поддержать по аналогии, если URL распознан, иначе — сообщение.

**Ошибки:** нет remote.origin — нотификация; файл не отслеживается git — нотификация.

## 6. Общие требования

### 6.1 Определение целевого репозитория (все команды)
Порядок: (1) выделение в проводнике/редакторе → маппинг через `RepositoryMapping`;
(2) иначе — если в воркспейсе один git-репозиторий, использовать его;
(3) иначе — диалог выбора из списка репозиториев воркспейса.
Ни одна команда не работает с репозиторием в состоянии rebase/merge/cherry-pick
в процессе (`Repository.getRepositoryState()` — must be SAFE, кроме команд,
явно обрабатывающих эти состояния).

### 6.2 Потоки и блокировки
- Вся работа JGit — вне UI-потока, через Eclipse Jobs с правилом `IWorkspaceRoot`
  (по аналогии с EGit).
- Диалоги блокировок индекса: использовать подход EGit, не дублировать.
- Прогресс: `IProgressMonitor`, осмысленные этапы («Спрятаны изменения», «Получение…»).

### 6.3 Autostash-примитив (общий для 5.1, 5.4, 5.5, 5.7)
Повторяемый механизм: «грязное дерево + операция, требующая чистоты»:
1. `StashCreateCommand` (имя `WIP @ <ветка> <время>`, включая untracked).
2. Целевая операция (checkout/pull/reset…).
3. `StashApplyCommand`; при успехе — `StashDropCommand`.
4. При конфликте или ошибке операции — стеш сохраняется, пользователь получает
   сообщение со ссылкой на view «Git Stashes». Никогда не делать drop без apply.

### 6.4 Безопасность данных (главное правило)
**Запрещено терять незакоммиченные изменения.** Любая операция, которая может
затронуть рабочее дерево, обязана: либо применить autostash-примитив, либо явно
попросить подтверждение. При любой неопределённости — остановиться с диагностикой,
оставив репозиторий в валидном состоянии.

### 6.5 Локализация
Ресурсы через `OSGI-INF/l10n` / `plugin.properties` + `plugin_ru.properties`.
Код — английские идентификаторы, сообщения — через Messages-классы (по образцу
`com._1c.g5.v8.dt.egit.ui`).

### 6.6 Сборка и доставка
- Maven + Tycho (`tycho-maven-plugin`), target platform — .target-файл с
  Directory-location на `/Users/nikitaaripov/.p2/pool/plugins` (путь параметризовать,
  см. `README.md`).
- Артефакты: p2-репозиторий + zip для `dropins` (проверенный способ установки,
  см. инструкцию its.1c.ru про самостоятельную разработку плагинов).
- Версионирование: `0.1.0.qualifier` → по схеме фаз.

### 6.7 Тестирование
- Headless-тесты логики core: JUnit, тестовые git-репозитории создаются программно
  (JGit, без сети). Покрыть: happy path + конфликт stash apply + отсутствие upstream +
  занятое имя ветки + состояние «не SAFE» + коммит уже в origin (5.6).
- UI-тесты: ручной чек-лист (ниже). Автотесты SWTBot — опционально, отдельной задачей.
- Ручной чек-лист (прогонять на EDT 2026.1):
  1. Smart Pull: без изменений; с изменениями; конфликт rebase.
  2. Quick Stash/Pop: пустое дерево, untracked, конфликт pop.
  3. Commit to New Branch: с возвратом/без; грязное дерево.
  4. Move Last Commit: существующая ветка; новая; конфликт cherry-pick.
  5. Undo Last Commit: локальный коммит (soft/mixed); коммит уже в origin (предупреждение).
  6. Smart Checkout: чистое/грязное дерево; конфликт.
  7. Sync: обычный; push rejected; upstream не настроен.
  8. Multi-repo: 2+ репозитория, один с ошибкой.
  9. Commit Guards: коммит в master (блок/подтверждение); сообщение без ключа задачи.
  10. Генератор сообщения: ветка с/без ключа.
  11. Open in GitLab: файл/ветка/коммит; self-hosted URL.
  12. После каждой операции — воркспейс консистентен (нет «висящих» блокировок индекса,
      Big Model переиндексировалась).

### 6.8 Настройки плагина
Preference page «Git Flow» (scoped: дефолт + per workspace):
- untracked в Quick Stash (bool, default true);
- шаблон автоимени стеша (string, default `WIP @ {branch} {date}` );
- защищённые ветки (comma-separated, default `master,main,develop`);
- regex ключа задачи (default `([A-Z]+-\d+)`);
- шаблон сообщения коммита (default `{key}: `);
- Open in GitLab: ref для ссылок на файл (HEAD-hash | branch, default HEAD-hash).

## 9. Открытые вопросы (решать при имплементации, фиксировать в коде/доке)

1. Нативный rebase autostash (JGit `PullCommand`) vs явный stash→pull→pop —
   выбрать по результатам прототипа на конфликтных сценариях (§5.1).
2. Шорткаты клавиш по умолчанию (не конфликтовать с штатными EDT; назначать не раньше фазы 4).
3. Иконка/брендинг плагина.
5. **Поставить EDT 2025.2.6 на Mac через 1cedtstart** (нужен дистрибутив под macOS
   с releases.1c.ru) и добавить `releng/edt-2025-2.target` для сборки точно под прод.
   До этого момента сборка — против пула 2026.1 с рейнджами `[6.0.0,8.0.0)`.
6. Для Quick Stash/Pop при отсутствии выбранного Git-ресурса и нескольких
   репозиториях показывается выбор репозитория (§6.1). В первой версии untracked
   включены всегда; настройка появится вместе с preference page (§6.8).
7. Для Move Last Commit применяется hard reset исходной ветки только после
   успешного cherry-pick (или создания новой ветки на том же коммите), возврата
   на исходную ветку и проверки чистого дерева. Dirty tree до этого сохраняется
   в стеше. Это исключает дублирование изменений, которое давал бы mixed reset.
8. Избранные ветки хранятся отдельно для каждого репозитория в настройках EDT;
   в дереве они показаны повторно в первой папке и не скрываются поиском.
   Удалённые ветки доступны для
   Smart Checkout, но не для Move Last Commit, который изменяет локальную ветку.
